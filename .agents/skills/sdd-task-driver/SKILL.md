# SDD 任务推进

每次从已记录的状态继续，推进到下一道尚未通过的审阅门槛。统一的是文档职责与交接方式；需求、技术方案和测试内容必须来自当前项目。

## 统一文件结构

先查找项目现有的功能文档目录；没有约定时使用 `doc/features/<功能名>/`。每个功能使用下列文件名。已有文件保留其领域内容、章节编号和条目前缀，只补齐与当前任务有关的缺口；其他名称的旧文档可作为草案来源，在审阅接受前不宣布新的文件取代旧的权威来源。

| 文件 | 应承载的内容 |
| --- | --- |
| `01_problem.md` | `Problem Statement`、`Current State`、`Goal`、`Non-goal` 和可验证的 `Success Criteria`（如 `SC-01`）。 |
| `02_architecture.md` | `Terminology / Glossary`、`Architecture Overview`、`Module Boundaries`、关键取舍及 `Architecture Evaluation`。 |
| `03_runtime.md` | `Runtime Flow`、`Data Flow`、`State Machine` 与 `Lifecycle`；不具有运行时的项目记录实际工作流程。 |
| `04_contracts.md` | `Contract`、`API / I/O`、数据约束、`Invariants` 与 `Compatibility`。 |
| `05_failures.md` | `Failure Policy`、带稳定编号的 `Failure Cases`（如 `F-<领域>-01`）、责任方与 `Recovery`。 |
| `06_decisions.md` | 逐项编号的 `ADR`（如 `ADR-001`），记录 `Status`、`Context`、`Decision`、`Alternatives` 与 `Consequences`。 |
| `07_test_plan.md` | `Test Strategy`、带编号的测试项（如 `STATE-01`、`ARCH-01`）、检查项状态语义与 `Traceability Matrix`；覆盖失败和边界条件。 |
| `08_tasks.md` | `Phase` 状态表、`Current Facts`（如 `CF-01`）、`Accepted Design Constraints`（如 `DC-01`）、`# TASK-XX <标题>` 当前任务简报与 `Completed Tasks`。 |

新项目缺少约定时，章节可采用 `1.`／`1.1` 层级，条目可参考上表的编号形式；具体测试类别和领域前缀由项目决定。沿用已有项目的现行编号和前缀，新增编号保持稳定并能在规格、任务、测试与审阅之间追踪。

同目录的 `Human_Review.md` 保存当前设计或完成审阅，包含 `Status`、`Task`、`Based on`、`Result`、审阅依据及逐项裁决；设计差异可使用 `DD-01` 等稳定编号。`_history/README.md` 说明信息所有权、归档准入、命名、证据格式及报告元数据；`_history/` 只保存正式预检、完成报告与已完成审阅等里程碑证据，不收纳临时想法或原始测试日志。

### 08 当前任务简报

对每个已启动且尚未完成交接的任务，在 `08_tasks.md` 的 `Next Gate` 与 `Completed Tasks` 之间保留独立的 `# TASK-XX <标题>` 简报。简报包含 `Status`、`Goal`、`References`、`Preconditions`、`Allowed scope`、`Must`、`Must not`、设计审阅裁决、验证计划或实际证据、`Handoff`；项目已有等价栏位时沿用原名。`Current Facts`、`Accepted Design Constraints`、`Next Gate` 和历史报告提供依据，简报则写出当前任务的具体执行与验收条件。

首次预检时建立简报；设计接受、实现、完成审阅各门槛均按实际进度刷新状态、裁决、验证和交接。若 08 只有 `Active Task` 单段摘要，先据现行规格、已接受审阅及报告补全简报，再继续推进。完成审阅待接受时保留简报；只有完成接受且项目要求的结束提交门槛已满足，才将任务移入 `Completed Tasks` 并切换下一任务。

## 建立基线并选择阶段

1. 从用户目标、代码和项目现有资料定位功能与任务。读取相关的 01–08、当前 review、`_history/README.md` 及必要的历史提交；现行 01–07 是已接受设计的来源，08 是当前任务状态，历史材料只解释过去。核对当前代码，不能把旧提交中的事实当成当前事实。
2. 检查版本控制和工作区。使用 Git 时记录分支、HEAD、已暂存与未暂存改动；没有 Git 时记录日期、关键文档及代码文件的相对路径和实际 SHA-256 摘要，作为可复核的工作树基线。保留已有用户改动，不编造提交、测试结果、批准或引用。
3. 缺少统一文件时，根据可核实的现状与用户目标自动建立所缺的 01–08 草案、`Human_Review.md` 待审阅稿及 `_history/README.md`。写出有依据的内容；未知的接口、取舍或验收条件明确列为待裁决项。沿用 08 已有任务编号；新功能没有编号约定时建议从 `TASK-01` 开始，后续递增且不复用旧编号。新草案在设计接受前不视为已接受规格，也不据此编码。
4. 从 08 和 review 恢复最早未完成的门槛。已有待验收的 Completion Report 时先处理完成审阅；已有设计裁决但尚未传播时先传播；不要重复生成报告或跳到下一任务。用户在本轮已明确接受的裁决直接沿用，不重复索取批准。

## 按门槛推进

先遵守项目已明确的审阅规则及用户当前指令；项目未规定时，默认设计实施前和任务完成时各需一次人工接受。

1. **预检：**对照 01–08、代码与历史证据核实当前事实、需求来源、边界、失败路径和测试映射。把基线、拟改动、待裁决设计差异、验证计划及 Ready/Blocked 结论写入 `_history/<任务ID>_preflight.md`；`Ready` 只表示可送审，不表示获准实施。在 `Human_Review.md` 准备 `Status: Pending Human Review` 的设计审阅稿；此时不传播未接受的决定，也不实施依赖它们的代码。
2. **设计接受后：**记录用户实际接受、拒绝或要求修改的逐项裁决。仅把已接受内容传播到相关的 01–07、ADR、07 的追踪关系和 08 的任务状态；新阶段与新测试仍保持未完成。若出现新的关键取舍，先补审阅，再继续依赖该取舍的实现。
3. **实现：**只做已接受的任务范围。行为代码优先补能暴露缺失行为的测试，再实现并运行针对性和项目全量验证；文档或其他不适用测试先行的变更用对应检查验证。审阅正确性、责任边界、失败路径与范围，修复具体发现后重跑受影响的检查。
4. **完成审阅：**已有 `_history/<任务ID>_completion.md` 时核对并复用；否则写明实际改动、执行过的命令及结果、边界检查、设计变化和剩余风险。在 `Human_Review.md` 准备待人工审阅的完成稿。接受前，08 的当前 `# TASK-XX` 简报保持待完成审阅，07 的新检查项、阶段及成功标准不勾选。
5. **完成接受后：**仅更新经审阅接受且有验证证据的检查项、阶段、成功标准和任务记录。若 Git 项目的已完成任务表要求结束提交，使用真实的实现或报告提交；尚未提交时提示该门槛，保留 08 的当前任务简报，暂缓填写提交引用及切换任务。无 Git 项目在同一栏注明无提交，并引用已记录的工作树基线。

测试通过、技术审阅、提交存在或设计审阅已接受，都不能替代完成审阅。审阅要求修改时保持当前门槛，修改并重新验证后再提交审阅。

## 审阅、归档与阶段交接

- 待审阅文件标明由 Codex 准备，写清任务、依据报告、拟议结论和具体裁决；只有用户或项目规则指定的审阅者明确接受后才改为 `Accepted Review`。覆盖当前已接受 review 前，先按 `_history/README.md` 归档一次；若缺少该 README，按上面的统一结构建立。归档副本只可补必要元数据，不改写原有裁决。
- 正式报告保留 `Status`、`Task`、`Baseline`、`Outcome`、`Source of Truth`；已接受 review 保留 `Status`、`Task`、`Based on`、`Result`、`Superseded by`。历史代码证据使用真实版本标识与仓库相对路径；无 Git 或未提交内容明确标注工作树证据。检查文档相对链接，不用本机绝对路径作导航。
- 07 中 `[ ]` 表示尚未实现或尚未通过对应审阅，`[√]` 表示已获接受且有验证证据；已勾选项成为后续回归条件。每阶段报告实际验证、改动、未决事项与下一门槛；有 Git 时检查 `git diff --check`，并给出限定文件范围的提交建议。只有当前任务在本次请求或此前会话中已有明确暂存或提交授权时才执行对应操作，提交前检查暂存差异并排除无关改动。
